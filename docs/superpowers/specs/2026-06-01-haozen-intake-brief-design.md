**תאריך:** 2026-06-01
**פרויקט:** `ninja-landing` (Astro 6 + Supabase + Vercel)
**סטטוס:** טיוטה לאישור

---

## 1. רקע ומטרה

הלקוח **האוזן** (מרכז שמיעה ישראלי, שני סניפים) רוצה לפצל את הנוכחות הדיגיטלית ל**שני אתרים**:

1. **האוזן** — מכשירי שמיעה, בדיקות, קופות חולים, אביזרים.
2. **אתר in-ear / מוזיקאים** — מוניטורים אישיים, אטמים, ציוד — מותג/חוויה נפרדים, עם קישורים הדדיים בין שני האתרים.

לפני שמתחילים לבנות, צריך **אפיון מלא מהלקוח**. הכלי: **דף נחיתה-טופס** באתר הסוכנות (`samp.ninja`) שהלקוח ממלא; התשובות **נשמרות** (Supabase) כדי שנדע בדיוק איך להתקדם.

**הגדרת הצלחה:** הלקוח ממלא את הטופס עד הסוף; כל התשובות שמורות ב-Supabase ונשלחת התראה לשרון; אנחנו מקבלים תמונת אפיון מלאה לשני האתרים.

> הערה: ה-spec הזה מתאר את **כלי האינטייק** בלבד. הבנייה בפועל של שני אתרי האוזן היא פרויקט נפרד שייצא מתוצאות הטופס.

## 3. ארכיטקטורה

עוקב אחר הדפוסים הקיימים בפרויקט (`contact.astro` → `api/lead.ts`, `lib/supabase.ts`).

```
src/pages/brief/haozen.astro      ← דף ה-wizard (prerender=false), Layout קיים + ברנד
src/pages/api/brief.ts            ← POST: honeypot, ולידציה, שמירה ל-Supabase, מייל Resend
src/lib/supabase.ts               ← קיים, ללא שינוי (server client)
supabase/migration_004_intake_briefs.sql  ← טבלה חדשה + RLS
```

**זרימת נתונים:**
1. הלקוח פותח `/brief/haozen` → ממלא wizard.
2. תוך כדי מילוי — טיוטה נשמרת ב-`localStorage` (שורד רענון/סגירה, ללא שרת).
3. בשליחה — `<form>` שולח את כל השדות ל-`POST /api/brief`.
4. ה-API: בודק honeypot → מוודא פרטי קשר → כותב שורה ל-`intake_briefs` (service-role client) → שולח מייל התראה לשרון + מייל תודה ללקוח (אם השאיר מייל).
5. הצלחה → עמוד/מסך תודה ("קיבלנו, נחזור אליך").

**למה Supabase ולא רק מייל (כמו `lead.ts`):** האפיון ארוך ומובנה; שמירה בטבלה נותנת דאטה מתוחזקת, ניתנת לחיפוש, ובהמשך נגישה מפורטל ה-admin הקיים.

## 4. סכמת Supabase — `intake_briefs`

```sql
create table public.intake_briefs (
  id            uuid primary key default gen_random_uuid(),
  created_at    timestamptz not null default now(),
  -- פרטי קשר
  business_name text not null,
  contact_name  text not null,
  phone         text not null,
  email         text,
  -- כל תשובות השאלון כאובייקט גמיש (סקציות ב-2-...)
  answers       jsonb not null default '{}'::jsonb,
  -- מטא
  source        text default 'brief/haozen',
  ip            text,
  status        text default 'new'   -- new | reviewed | in_progress | done
);

alter table public.intake_briefs enable row level security;
-- כתיבה רק דרך service-role (ב-API route); קריאה רק ל-admin_users.
create policy "admins read briefs" on public.intake_briefs
  for select using (exists (select 1 from public.admin_users a where a.user_id = auth.uid()));
```

`answers` כ-JSONB: גמיש לשינויי שאלון בלי מיגרציות; כל סקציה היא מפתח. (אם נעדיף עמודות מפורשות בהמשך — קל לגזור מ-JSONB.)

## 5. מבנה ה-Wizard (8 סקציות)

פס-התקדמות + ניווט הבא/הקודם. רק **סקציה 1 (פרטי קשר)** חובה; השאר ניתנות לדילוג כדי לא לחסום שליחה. כל שדה ממופה למפתח ב-`answers`.

> מקרא סוגי שדה: `[רדיו]` בחירה יחידה · `[צ׳ק]` בחירה מרובה · `[טקסט]` שורה · `[פתוח]` טקסט ארוך.

### סקציה 2 — תמונה כללית והפרדה ⭐
- מבנה הדומיינים: שני דומיינים נפרדים / תת-דומיין / תיקייה `[רדיו]` + פרטים `[פתוח]`
- המותג של אתר ה-in-ear: ממשיך כ"האוזן" / מותג נפרד `[רדיו]` + שם אם יש `[טקסט]`
- הקישור בין האתרים: תפריט / באנר / כפתור `[צ׳ק]`; דו-כיווני? `[רדיו]`
- הסיבה העיקרית להפרדה `[פתוח]`

### סקציה 3 — אתר האוזן (מכשירי שמיעה) ⭐

## 6. עיצוב

- **Layout:** מבוסס `Layout.astro` הקיים (RTL, פונטים, ניווט מוסתר/מינימלי לדף פרטי).
- **פלטה:** רקע `#08090c`, פעולה `#ff2a3c`, אקסנט-פרימיום `#ffd166`, טקסט `#f5f5f7`, משני `#a8acb6`.
- **טיפוגרפיה:** כותרות Rubik (700–900), גוף Heebo (300–500).
- **רכיבים:** כרטיס wizard ממורכז, פס-התקדמות עליון, שדות גדולים ונגישים, כפתורי הבא/הקודם, מסך תודה ממותג (שוריקן).
- **טון:** "שקט וחד" — בלי קלישאות, ישיר.

- בנייה בפועל של שני אתרי האוזן (פרויקט נפרד שייגזר מהתוצאות).

- שמירת טיוטה חוצת-מכשירים בשרת (כרגע `localStorage` מספיק).
